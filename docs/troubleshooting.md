# 故障排查

先保留原文和当前输入，再检查状态。不要反复调用模型、删除数据卷或直接覆盖数据库。

## 暂存与会议

| 现象 | 先做什么 | 不要做什么 |
| --- | --- | --- |
| 正在保存一直不结束或保存失败 | 保持页面，检查网络，重试保存；必要时复制输入，手动工作台可下载当前输入 | 不要刷新、清浏览器数据或关闭未保存页面 |
| 需要补建项目/人员 | 使用会议工作台的原地创建，AI 审阅使用新建并返回本项 | 不要开空白会议重新粘贴一遍 |
| 多标签冲突 | 先保留旧页修改，再打开最新草稿，人工补回缺失项 | 不要把旧页当作较新版本强制覆盖 |
| 当前任务已被修改 | AI 点「保留修改并重新核对当前任务」后检查差异；手动记录保留输入，移除旧卡再重新选择最新任务 | 不要把重新核对当作自动同意覆盖 |
| 登录过期 | 保留输入，在另一标签登录同一站点，再回原页重试；仍失败则先核对服务器最新草稿 | 不要在未备份输入时直接刷新 |
| 历史会议没有改变当前进度 | 这是历史保护；查看会议日期对应的时间线/周报。需要更新当前任务时另记今天的真实进展 | 不要把旧会议日期改成今天来规避保护 |
| 未来会议不能确认 | 保留草稿，到会议当天再确认；日期误填则先修正 | 不要提前记为已完成 |

手动工作台的冲突 JSON 用于人工核对，没有自动导回。断电和强制退出可能丢失未到达服务器的输入；日常离开前确认「已暂存」。

## AI 解析失败或很慢

1. 在会议列表查看是等待、处理中还是失败。设置页显示队列和最长排队时间，不会调用模型。
2. 等待长期不动：检查 worker 容器是否运行。心跳表示进程存活，不保证每个模型请求都成功。
3. 正在处理：服务商生成时间、网络延迟和格式修复都算在模型总 deadline 内；网页本身无需等模型返回。部署到美国不能保证所有模型请求变快。
4. 失败后查看错误说明，确认 key、模型名、服务地址及余额/限额。不要把 API Key 或完整 env 发到群里或工单中。
5. 修正环境变量后重建 app 和 worker；单独改 env 文件不会改变现有进程环境。
6. 需要重试时使用现有会议的重试入口，不要反复新建同一份原文。重试可能产生服务商费用。

服务器只读检查示例（进入代码目录，替换为实际配置路径）：

```bash
docker compose --env-file /etc/meeting-progress-tracker/server.env -f docker-compose.server.yml ps
docker compose --env-file /etc/meeting-progress-tracker/server.env -f docker-compose.server.yml logs --tail=80 app worker
```

日志可能包含业务信息，分享前应脱敏。修改配置后的重建命令见 [维护手册](operations.md)。

新版 worker 默认输出安全的单行 JSON 诊断：`context` 是上下文准备，`first_call` 是首次模型请求，`repair_call` 只在格式修复时出现，`persistence` 是草稿写入，`total` 是端到端时间，`model_total` 是模型处理部分。按同一 `meeting_note_id` 对照 `duration_ms`，即可判断时间主要耗在哪里。日志只输出阶段、时长和数量白名单，不含模型原文、完整响应或 key；其他 Docker/代理日志仍需单独脱敏。这是诊断能力，不是对实际服务商速度的保证。

## 网页与部署

| 现象 | 检查顺序 |
| --- | --- |
| 域名无法访问 | DNS 指向、可用 IPv4/IPv6、80/443、防火墙、Caddy 日志 |
| 登录后 403 / CSRF | 当前域名与 APP_DOMAIN 是否一致，是否使用 HTTPS，反代是否正确传递 Host 与协议 |
| /health/ 成功但功能不可用 | /health/ 只检查网页进程；/ready/ 才检查数据库表是否可读取。再检查 app 日志与迁移是否成功 |
| 新版页面没出现 | 核对设置页版本、当前镜像和容器是否已重建；不要靠清数据库解决 |
| 恢复提示目标已存在 | 选择新、未使用的数据卷；不要先启动 app 创建空库再恢复 |
| 恢复提示权限问题 | 用维护脚本的私密流式恢复流程，不直接将宿主 0600 文件挂给不同 UID，不设 644/777 |
| 修改 env 的 ADMIN_PASSWORD 没生效 | 它只用于首次建号，已有账户请在设置中修改密码 |
| SQLite locked / 磁盘已满 | 保持单 app/worker、小数据本地磁盘；检查磁盘空间及备份保留，不在网络文件系统共享数据库 |

不要运行 `docker compose down -v`，不要在恢复前删除原数据卷。升级失败时先保持停写，再按 [维护手册](operations.md) 选择旧镜像与对应快照回退；回退数据库会丢失快照之后的写入，应先保留故障现场。

## 导出、备份与恢复的区别

- JSON/CSV 是业务查阅导出，不是完整迁移文件。
- SQLite 备份包含账户、手动会议暂存、AI 草稿、计划和队列；env 的密钥不在数据库备份中，要单独安全保存。
- 设置页的最近成功快照只表示曾成功校验，不代表文件仍在，也不代表异地转存成功。
- 同盘副本不能抵御磁盘损坏；异地副本也要做一次恢复演练才知道流程可用。
- 不要同时在旧机和新机继续记两套数据，SQLite 文件不会自动合并。
